# Module 8: Procedural Logic and Final Project Revision

### Purpose

- Add reusable procedural logic where justified.
- Use final-project revision to test whether students can adapt the whole database solution when requirements change.

### Objectives

- decide when a stored procedure is appropriate
- decide when a trigger is justified
- test procedural behavior with controlled inputs and changes
- revise the full project package for cross-artifact consistency after a new rule or constraint

### Human Must Know

- whether a procedure or trigger should exist at all
- what counts as expected behavior
- how one business-rule change propagates across artifacts and implementation
- how to judge cross-artifact consistency in the final package

### AI May Assist With

- drafting stored procedures and triggers
- generating test cases
- executing procedural logic and capturing outputs
- checking consistency across SQL files and design artifacts

### Christian Integration Focus

- frame automation as delegated authority that must remain bounded, testable, and accountable
- present revision, consistency, and final packaging as marks of faithful professional follow-through

### Integration Touchpoints

- include one procedural-choice prompt asking what should not be automated because human judgment or fairness still matters
- include one final-project checkpoint asking whether the finished package is coherent, honest about limitations, and trustworthy for the stated business purpose

### Lessons

#### Lesson 8.1: Stored Procedures
- procedure purpose
- reusable operations
- parameter use
- basic testing

#### Lesson 8.2: Triggers
- trigger purpose
- event-driven logic
- justified rule enforcement
- behavior testing

#### Lesson 8.3: Final Project Integration and Revision
- review the full project package
- detect inconsistencies
- revise the project after a change request

### Assessment Strategy

This module should not end with a polished project package alone. AI can produce and revise that package. The stronger assessment is to force a late change and evaluate how well students revise and defend the integrated solution.

### Primary Graded Assessment

#### Change Request Revision

- Format: students receive a late business-rule change after building or reviewing a project package
- Students explain what changes in the ERD, DBDD, SQL implementation, views, procedures, triggers, permissions, or tests, and submit the revised pieces with justification

### Secondary Evidence

- short procedural-logic justification task
- annotation or screencast defending one stored-procedure or trigger decision

### What To Grade

- whether the procedural choice is justified
- quality of test reasoning
- completeness of cross-artifact revision
- clarity about what changed and why
- ability to explain whether the automation or final package is fair, bounded, accountable, and trustworthy in the case

### Module Assessment Tasks

- decide whether a task belongs in a plain query, stored procedure, or trigger
- explain expected versus unexpected behavior for procedural logic
- identify which project artifacts must change after a new rule arrives
- revise the project package and justify the revisions

### Why This Assessment Holds Up Better

- it makes adaptation the core performance
- it tests whether students understand the whole system, not just one artifact
- it treats AI-generated project material as draft input, not final proof of learning
